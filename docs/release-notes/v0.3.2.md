# Mactoy v0.3.2 — enclosure quirk warnings + post-install verification + retry

Small hardening release. Four issues from the tracker landed as fixes; thanks to [@dewet22](https://github.com/dewet22) for [#4](https://github.com/cashcon57/mactoy/issues/4) (the RTL9210B XHCI-stall writeup is exceptional) and [@dmurvihill](https://github.com/dmurvihill) for [#1 followup](https://github.com/cashcon57/mactoy/issues/1), [#5](https://github.com/cashcon57/mactoy/issues/5), and [#6](https://github.com/cashcon57/mactoy/issues/6).

## What's new

### Pre-flight quirky-enclosure banner ([#4](https://github.com/cashcon57/mactoy/issues/4))

Some USB bridges are known to stall under Mactoy's sustained raw write pattern — the **Realtek RTL9210 / RTL9210B** in particular, on Apple silicon Macs. The stall escalates into a full XHCI controller reset, tearing down every downstream USB device including internal hubs on Mac minis. The raw fd Mactoy holds dies with the bus (ENXIO), the write fails mid-flight, and the drive is left in an indeterminate state. Root cause is bridge firmware × Apple XHCI interaction — Mactoy can't fix it, but can warn about it and suggest the known workaround.

v0.3.2 adds a **`QuirkyEnclosureRegistry`** (in `MactoyKit`) that matches `DiskTarget.mediaName` against a curated list of known-quirky bridges. Match hit → pre-flight banner appears above the danger banner in both Install Ventoy and Update Ventoy panels. **Non-blocking** — user can proceed if they want to. Banner spells out the symptom + the workaround (usually: force USB 2.0 to fall back to Bulk-Only Transport, which avoids the stall) + a link to the source issue for context.

Seed entry: **RTL9210 / RTL9210B**. PRs adding entries welcome — the registry is a public constant with a comment block explaining the criteria (specific substring, symptom description, workaround, ideally a reference issue).

### Better ENXIO error message ([#4](https://github.com/cashcon57/mactoy/issues/4))

If the write DOES fail with ENXIO despite the banner (or on a bridge we haven't listed yet), `DiskWriter` now surfaces a targeted message instead of the generic disk-I/O error: explains what actually happened, suggests the USB 2.0 workaround, tells the user the disk is in an incomplete state and to re-run Install Ventoy. Actionable copy in the failure banner, not a raw errno string.

### "Re-check disk" button always visible ([#6](https://github.com/cashcon57/mactoy/issues/6))

Previously the "Try again" affordance in the Update Ventoy panel only appeared when the probe FAILED. Users diagnosing post-install oddities (see #5) had no way to force a re-probe on demand. v0.3.2 adds an always-visible **Re-check disk** button at the bottom of the Update Ventoy panel whenever a disk is selected — pass or fail state, doesn't matter.

### Post-install verification ([#5](https://github.com/cashcon57/mactoy/issues/5))

The reporter hit a case where Mactoy's install reported **success** but the disk was actually not bootable — the USB stick was hardware-faulty (Ventoy2Disk on Windows failed on the same drive with a "read-back doesn't match write" error). Mactoy trusted the driver's "done" signal without verifying the write actually produced a valid Ventoy layout.

v0.3.2 fixes this: after both `executeFreshInstall` and `executeUpdate` finish their final remount, run `VentoyVersionProbe.probe(bsdName:)` and throw `DriverError.validation` if `isVentoyDisk == false`. The failure message names the specific layout issues and explains that this usually means a hardware fault on the USB stick, with a suggestion to try a different drive.

### "Retry install" button on the failure banner ([#5](https://github.com/cashcon57/mactoy/issues/5))

When `run()` ends in `.failed`, Mactoy now preserves the captured target/mode from the confirmation so the failure banner can offer a **Retry** button next to Done. Retry re-runs against the *same* disk without going through the confirmation sheet again. Layers 4/5/6 of the iron-clad targeting defense (v0.3.1) still verify the disk hasn't drifted at retry time, so the safety guarantee is unchanged — this is just spared clicks after a hardware-level failure.

### README v0.3.0 → v0.3.1 ([#1 comment](https://github.com/cashcon57/mactoy/issues/1#issuecomment-4382109064))

Four references corrected: status header ("v0.3.1 alpha"), Update Ventoy feature line, install command reference DMG name, build-dmg command example.

## Known limitations

- **Post-install verification is best-effort.** If the probe itself flakes (transient disk unavailability right after remount), the install could be flagged as failed when the write actually succeeded. Rare; retry usually resolves it.
- **Quirky-enclosure registry starts small.** Only RTL9210 seeded. If your enclosure hangs the write on Apple silicon with a similar unified-log signature (see #4), please file an issue with a `log show --predicate 'subsystem == "com.mactoy"' --last 1h` capture and I'll add it.

**SHA256 of `Mactoy-0.3.2.dmg`** is published below the release assets.
